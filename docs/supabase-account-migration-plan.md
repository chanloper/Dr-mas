# 기존 MariaDB 계정 이전 계획 (미실행)

## 보존 원칙

Cloudtype MariaDB, Users, 기존 계정·bcrypt 해시·웹 세션·mobile-api 토큰은
수정하거나 삭제하지 않는다. 앱의 Supabase 전환은 기존 계정을 자동으로
Supabase에 복제하거나, MariaDB 로그인 성공을 Supabase 인증으로 인정하지 않는다.
로컬 AsyncStorage의 기기별 복약 체크도 사용자 소유가 확인된 임상 기록이
아니므로 자동 업로드하거나 특정 새 계정에 붙이지 않는다.

## 권장하는 별도 승인 절차

1. 기존 login_id와 신뢰할 수 있는 이메일의 대응 여부를 담당자가 확인한다.
   아이디 문자열이 이메일처럼 보여도 소유권을 추정하지 않는다.
2. 사용자가 기존 계정 소유권과 새 이메일 소유권을 검증한 후, Supabase
   이메일 인증 및 비밀번호 설정/초대 절차로 새 UUID를 확보한다.
3. 관리자 전용의 비공개 매핑 저장소에 legacy user_id와 새 UUID, 검증 근거,
   처리 일시를 기록한다. 현재 마이그레이션에는 매핑 테이블이나 자동 이전
   스크립트를 넣지 않았다. 유일성·접근권한·보관 기간을 먼저 승인해야 한다.
4. patient/guardian 역할과 연결·환자 동의를 다시 확인한다. 기존 서비스의
   역할 선택이나 클라이언트 metadata를 권한 증거로 이전하지 않는다.
5. 데이터 범위·동의·날짜/시간대·중복 제거·검증 기준을 확정하고 별도 개발
   환경의 가상 데이터로 검증한 후에만 승인된 이관 도구를 작성한다.
6. 기존 서비스를 유지한 채 단계별 전환, 대조 검증, 취소/복구 절차를 둔다.
   일정 기간 이중 서비스를 운영한다면 계정 비밀번호·로그아웃·데이터가
   자동 동기화되지 않는다는 점을 명확히 안내한다.

## 비밀번호와 토큰

MariaDB의 bcrypt 해시를 PostgreSQL의 일반 프로필 테이블에 복사하거나
평문 비밀번호를 수집하지 않는다. 기본 계획은 이메일 소유권 검증 후 새
비밀번호 설정이다. 해시 가져오기를 별도로 검토하려면 그 시점의 Supabase
지원 방식·알고리즘·보안 통제·실패 복구를 검증하고 별도 승인해야 한다.
현재 준비에는 관리자 키, 원본 비밀번호, 추출 쿼리나 실제 사용자 데이터가 없다.

MariaDB opaque token과 웹 express-session 쿠키는 Supabase JWT/refresh token으로
교환하거나 그대로 재사용하지 않는다. 기존 보안 이슈의 키 교체·Git 이력
노출 대응도 Supabase 전환만으로 해소되지 않는다.

이 문서는 계획만 제공하며 DB 접속·읽기/쓰기, 계정 생성/초대, 원격 변경,
배포, Git commit/push를 수행하지 않았다.
