# 실제 MariaDB · HTTP 인증 통합 검증

검증일: 2026-11-01 (Asia/Seoul), 브랜치: DrMAS-Mobile

## 결과

**MariaDB 12.2.2 + 실제 HTTP에서 28/28 항목 통과.**
기존 백엔드 17건과 모바일 서비스·프로세스 내부 통합 16건도 재실행하여
총 61건이 통과했다. 서버·추가 스크립트의 구문 검사와 git diff --check도
통과했다. 비밀정보 검사는 아래 기존 후보 8건 때문에 검토 필요 상태다.
Cloudtype 운영 DB에는 접속하거나 변경하지 않았다. 기존 로컬 MariaDB
서비스도 접속·변경·중지하지 않았다. mas_project 및 모바일 UI는 이 단계에서
수정하지 않았다. 배포와 Git commit/push도 수행하지 않았다.

## 격리 환경

- Docker CLI는 PATH에서 찾지 못했다. Windows MariaDB 서비스와 설치된
  MariaDB 12.2.2 바이너리를 확인하여 별도의 인스턴스를 사용했다.
- 기본 데이터 폴더·설정 파일·기존 DB 접속정보를 재사용하지 않았다.
  `.env`를 로드하지 않고 로컬에 새 데이터 디렉터리를 초기화했다.
- 최신 성공 실행의 데이터 디렉터리는
  `.local-auth-tests/run-uZqBUI/data`이며 비식별 결과는 같은 실행 폴더의
  `results.json`에 보관했다. 이 폴더는 Git에서 제외된다.
- DB와 HTTP는 모두 `127.0.0.1` 임시 포트에만 바인딩했다. DDL 전 실제
  `@@datadir`와 `@@port`가 새 인스턴스와 일치하는지 확인했다.
- 생성한 두 DB의 이름은 `drmas_auth_test_`로 시작한다. 관리용 연결은
  테스트 초기화·검증에만 쓰고, API 연결은 별도 계정의 SELECT/INSERT 및
  세션 DELETE 권한으로 제한했다. 런타임 API 계정에는 DDL 권한이 없다.
- root·API DB 비밀번호는 매 실행 무작위로 생성하며 값을 출력하거나
  Git 대상 설정파일에 저장하지 않는다. 계정·비밀번호·토큰은 모두 가상이다.
- 종료 시 HTTP 서버, 커넥션 풀과 생성한 MariaDB 프로세스를 종료했다.
  기존 서비스를 종료하거나 기존 DB를 삭제하는 동작은 없다.

## 재현한 스키마

1. `database/schema.sql`의 Users: username VARCHAR(30), gender ENUM.
2. `mas_project/server.js`의 Users: username VARCHAR(100), gender VARCHAR(20).

각 파일에서 Users CREATE 문만 추출해 새 DB에 실행했다. schema.sql 전체의
DROP 문이나 기존 서버의 초기화 코드는 실행하지 않았다. 각 DB에 가상의
기존 사용자 1명을 넣고 실제 bcrypt cost 10 해시를 저장한 뒤,
`database/migrations/001_mobile_auth.sql`의 두 CREATE 문을 적용했다.

실제 Express 앱을 listen하고 fetch로 요청했다. 단위 테스트의 핸들러
직접 호출이나 가짜 connector를 사용하는 결과가 아니다. 다만 전송은
로컬 HTTP로 한정하며 TLS·Cloudtype 프록시·실제 기기는 검증하지 않았다.

## 발견 사항

- 첫 실행은 24/28이었다. 초기 비교 테스트가 롤백 후 AUTO_INCREMENT
  카운터까지 불변이라고 가정하여 4건이 실패했다. 가입 시도 후 롤백되면
  행이 없어도 카운터가 증가할 수 있다. 제품 결함은 아니며 기존 문서에도
  명시된 정상 동작이다. 마이그레이션 직전/직후는 전체 정의를 비교하고,
  전체 가입 시나리오 종료 후에는 카운터만 제외해 정의를 비교하도록
  수정했다. 행·비밀번호 해시·컬럼·인덱스·엔진 검사는 유지했다.
- 가입·조회·트랜잭션·폐기 경로에서 새로운 제품 코드 오류는 발견하지
  않았다. 따라서 API의 런타임 소스와 마이그레이션 SQL은 변경하지 않았다.
- 보호자 승인·기존 계정 이메일 연결은 여전히 운영 정책과 별도 절차가
  필요하다. 테스트에서는 관리용 연결로 가상 계정만 명시적으로 연결했다.
- 모바일 로그아웃은 아직 로컬 삭제만 한다. 이번에 서버의 토큰 폐기
  API는 검증했지만 모바일의 폐기 API 호출 연결은 별도 작업이다.

## 비밀정보 및 Git 점검

- 실제 `.env`, `.env.local`, `.env.test`와 테스트 DB 데이터 폴더가 Git에서
  제외되는 것을 `git check-ignore`로 확인했다. 빈 `.env.example`은 공유한다.
- `.gitignore`에 `.env.*` 및 `.local-auth-tests/` 규칙을 추가했다.
- 이번에 작성한 실행기·결과·설정 예시에서는 실제 자격증명을 기록하지
  않았다. 비밀 검사 출력도 파일·줄·변수·규칙 이름만 포함한다.
- 기존 추적 파일에는 **검토 후보 8건**이 있다. 실제 비밀값인지 예시인지
  자동 판정하거나 외부 서비스에 유효성을 조회하지 않았다. 값은 출력하지 않았다.

| 기존 파일 | 검토 대상 |
| --- | --- |
| mas_project/env.example | DB_PASS, GEMINI_API_KEY, PUBLIC_API_KEY, KAKAO_REST_API_KEY |
| mas_project/server.js | 하드코딩된 세션 secret |
| src/backend/.env.exapmle | DB_PASS, GEMINI_API_KEY, PUBLIC_API_KEY |

mas_project 수정 금지 범위와 기존 파일 보존을 유지하여 후보를 임의로
변경하지 않았다. ignore 규칙은 이미 추적된 값을 제거하지 않는다.
따라서 저장소 전체에 비밀정보가 없다고 보증할 수 없으며, push 전 사람이
예시 여부를 확인해야 한다. 실제 비밀이라면 발급처에서 교체하고 현재
파일과 Git 이력의 노출 대응을 별도로 승인·처리해야 한다. 검사는 휴리스틱이며
Git 이력 전체는 검사하지 않았다.

## 재실행

설치된 바이너리 경로를 사용하여 프로젝트의 mobile-api 폴더에서 실행한다.
기존 .env나 운영 DB 접속정보를 넣지 않는다.

```powershell
npm.cmd run test:live -- --run-isolated-local --mariadb-bin 'C:\Program Files\MariaDB 12.2\bin'
node scripts/check-secret-files.cjs
```

두 번째 명령은 위 기존 검토 후보 때문에 종료 코드 1을 반환한다.
실행기는 바이너리가 없으면 중단하며 DB 설치·서비스 등록·운영 접속으로
대체하지 않는다. 실행마다 새 로컬 폴더를 사용하며 데이터를 재사용하지 않는다.

## Cloudtype 적용 전 다음 절차 (미수행)

1. 기존 파일의 비밀 후보를 검토하고, 실제 값이면 교체·노출 대응한다.
2. 운영의 실제 MariaDB 버전·Users 정의·InnoDB·키 타입·문자셋·시간대·
   추가 필수 컬럼·트리거를 담당자가 확인한다. 이번 12.2.2 결과만으로
   다른 버전이나 실제 운영 스키마의 호환성을 단정하지 않는다.
3. 해당 버전의 별도 테스트 인스턴스와 가상 데이터에서 같은 검사를
   반복한다. 운영 DB를 이 실행기에 연결하는 옵션은 제공하지 않는다.
4. 기존 계정 연결·보호자 승인·환자 동의 정책을 확정하고,
   마이그레이션의 잠금·부분 적용 복구 계획과 백업 복원 절차를 검토한다.
5. 별도 승인을 받은 후에만 운영 백업과 additive migration 적용,
   최소 권한 API 계정 생성·설정, API 배포를 진행한다. 운영 전환은
   기존 웹서버 시작이나 database/schema.sql 초기화로 대체하지 않는다.
6. HTTPS·프록시·DB 전송 보안·공유 rate limit 및 모니터링을 검증한 뒤
   실제 API URL을 모바일에 설정하고 iOS/Android 통합 검사를 진행한다.
7. 서버 폐기 API를 모바일 로그아웃에 연결하는 작업과 만료 세션 정리,
   이메일 검증·비밀번호 재설정·토큰 갱신 정책을 별도로 마무리한다.
