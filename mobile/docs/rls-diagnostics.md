# 실제 사용자 세션 RLS 일회성 진단

## 실행 조건

원격 SQL/RPC 실행이나 계정 생성 없이, 기존 getSupabaseClient()의 로그인 세션으로
auth.getUser(), 본인 profiles 조회, HEAD/count 방식 SELECT만 실행한다.
관리자 키나 JWT 입력 기능은 없다. 실제 의료/환자 계정에 사용하지 않는다.

다음 세 조건이 모두 필요하다. 실제 프로젝트 연결도 기존 클라이언트에 저장된
origin과 EXPO_PUBLIC_EXPECTED_SUPABASE_REF를 비교해 Boolean으로만 검사한다.

- __DEV__ = true (개발 빌드/개발 서버)
- EXPO_PUBLIC_APP_ENV=development
- EXPO_PUBLIC_RLS_DIAGNOSTICS=1 (새 명시적 활성화 플래그, 기본 비활성)

기존 환경 설정을 보존하면서 로컬 PowerShell에서 플래그를 추가한다.
이미 development 및 예상 Dev 프로젝트가 설정돼 있는지 먼저 확인한다.

```powershell
Set-Location C:\MAS\Dr-mas\mobile
$env:EXPO_PUBLIC_RLS_DIAGNOSTICS = '1'
npm.cmd start
```

현재 개발 서버를 이미 실행 중이면 종료 후 이 설정으로 다시 시작하고 앱을 다시 연다.
비밀번호·JWT·UUID를 환경변수나 파일에 추가하지 않는다. 프로덕션 환경을 임의로
development로 바꿔 우회하지 않는다.

## 화면 접근과 계정별 실행

설정 화면의 **RLS 보안 검사** 버튼으로 연다. 위 개발 조건이 모두 맞을 때만
버튼이 보이며, 일반 실행·배포 앱에서는 숨겨지고 직접 경로 접근도 차단한다.
URL 입력은 필요 없다. 선택적으로 사용하는 개발용 웹 주소는
`http://localhost:8081/_dev/rls-check` (실제 개발 서버 포트를 사용).
Expo Go는 현재 개발 서버 주소 뒤에 `/--/_dev/rls-check`를 붙인 링크를 연다.
예: `exp://<개발-PC-주소>:8081/--/_dev/rls-check`.
URL이나 쿼리 파라미터로 계정 UUID/토큰을 전달하지 않는다.

1. 기존 앱에서 합성 A로 로그인하고 설정 → RLS 보안 검사를 누른다.
2. A를 선택하고 합성 A/G UUID를 마스킹 입력란에 직접 입력한다.
   현재 프로젝트와 합성 계정임을 확인한 후 읽기 전용 검사를 누른다.
3. A 본인 프로필 1행, A 일정/기록 각각 1행 이상, A-G 이력 1행 이상,
   현재 승인 연결 정확히 1행이 모두 PASS여야 한다. SOS 전체 이력과 G 수신 이력도
   각각 1행 이상이어야 SOS 기준이 생성된다. 새 SOS를 보내는 기능은 없다.
4. '앱으로 돌아가기'로 기존 앱에 이동해 로그아웃하고 G로 로그인한다.
   설정 → RLS 보안 검사로 돌아와 G를 선택하고 같은 A/G를 입력한다.
5. G의 SOS 두 항목이 PASS인 것을 확인한 후 같은 방식으로 B/H를 검사한다.
   G 검증 전 B/H SOS 0행은 미검증이다. 계정별 로그인이 성공했는지 앱에서 확인한다.
   A/G는 실제 사용자 ID까지 대조한다. B/H 라벨은 운영자가 선택하므로,
   B/H가 의도한 합성 계정인지는 로그인 단계에서 직접 확인해야 한다.

동일 앱 JS 실행 환경에서 A의 성공 기준을 최대 15분 동안만 메모리에 유지한다.
앱/브라우저 새로고침, 프로세스 재시작, 다른 기기는 기준을 공유하지 않는다.
이 경우 각 실행 환경에서 A를 다시 먼저 확인한다. 다른 기기/세션의 0행을 임의로
PASS로 해석하거나 운영 데이터를 기준으로 삼지 않는다.
입력은 실행 종료 시 지우고, 결과는 세션 변경/화면 이탈 후 숨긴다. 파일 저장,
원문/식별자 로그, 결과 업로드는 없다. 기준은 실제 데이터를 보관하지 않고
A/G 입력 참조와 건수만 일시적으로 유지한다. 테스트 중 합성 자료나 연결을 바꾸지 않는다.

## 기대 결과

| 사용자 | 본인 프로필·역할 | A 일정·기록 | A-G 전체/승인 연결 | A 프로필 |
|---|---|---|---|---|
| A | 본인 1행 / patient | 1행 이상, 기준 생성 | 이력 존재 / 승인 1행 | 본인 조회로 확인 |
| G | 본인 1행 / guardian | A 기준 건수와 일치 | A 기준과 일치 / 승인 1행 | 0행 |
| B | 본인 1행 / patient | 0행 | 0행 | 0행 |
| H | 본인 1행 / guardian | 0행 | 0행 | 0행 |

SOS 추가 검사:

- A: patient_id=A 전체 SOS와 patient_id=A, guardian_id=G SOS 각각 1행 이상.
- G: 두 조회 모두 A가 확인한 G 수신 건수와 같고 1행 이상. A 전체 건수와는
  다를 수 있다(다른 승인 보호자 수신분은 G에게 노출되면 안 됨).
- B/H: 두 조회 모두 오류 없이 0행. H는 H-A 승인 연결 0건도 확인한다.
- SOS 양성 기준은 A→G의 현재 일반 사용자 세션 조회로만 생성하고 15분 동안
  메모리에서만 유지한다. 0건/오류/기준 만료/지우기 후 차단 PASS를 만들지 않는다.
- 화면에는 항목명, 오류 여부, 건수, 판정만 표시한다. 원문이나 식별자는 조회 결과로
  표시·로그·파일 저장하지 않는다. 실제 Dev 실행 전까지 새 SOS 검사는 미검증이다.

H 자신의 다른 대기·종료 연결 조회를 금지하는 테스트가 아니다. A-G 조합만 필터한다.
HTTP/인증/스키마 오류는 차단 PASS로 간주하지 않는다. 유효한 A 기준 없이 0행이면
미검증(A_BASELINE_REQUIRED), 예상 밖 노출이 있으면 기준 유무와 관계없이 FAIL이다.
실행 중 세션이 바뀌거나 제한시간(45초)이 지나면 부분 PASS를 폐기한다.
가입·로그인·토큰 갱신은 기존 앱/Auth에서 수행하며 진단은 DB 쓰기/RPC를 호출하지 않는다.

## 테스트 후 제거

개발 서버를 종료하고 `Remove-Item Env:\EXPO_PUBLIC_RLS_DIAGNOSTICS` 후 다시 시작한다.
앱을 다시 로드하면 메모리 기준이 사라진다. 화면의 기준 지우기도 사용할 수 있다.
일회성 파일은 src/dev/ 두 파일, src/app/_dev/rls-check.tsx,
scripts/test-rls-diagnostics.cjs와 이 문서로 분리했다. 제거 시 _layout.tsx의
보호 경로 선언, SettingsScreen.tsx의 개발 전용 버튼/가져오기와 supabase.ts의
Boolean 프로젝트 확인 함수/캐시만 함께 정리한다.
기존 로그인·복약·AI·SOS 화면을 수정할 필요는 없다.

현재 실제 A/B/G/H JWT 실행 결과는 미검증이다. Mock 검사 통과를 Dev RLS PASS로
취급하지 않는다. 관리자 SQL 결과 역시 사용자 RLS 증거가 아니다.
