# SOS 요청과 보호자 확인

## 구현 범위

환자 홈 SOS 버튼 → 설정의 10/20/30초 대기(취소 가능) → 서버에 승인된 보호자별
요청 저장 → 다른 기기의 보호자 홈 수신함에서 조회·확인 → 환자 홈 내역에 확인 시각 표시.
홈의 SOS 패널이 열리고 앱이 전경일 때 15초마다 조회한다. 새로고침도 제공한다.
화면 이탈·백그라운드 전환 시 미전송 대기를 취소한다. 서버 요청이 이미 시작되었다면
취소를 보장하지 않으며 내역에서 결과를 확인해야 한다.

백그라운드 푸시, 소리·진동, 위치 전송, 119 신고, 보호자의 실제 구조 활동은 구현하지 않았다.
요청 저장 성공은 보호자 확인 성공이 아니다. 통신 실패는 자동 재전송하지 않는다.
수신함은 미확인 우선 최대 50건이며 전체 이력 화면은 후속 작업이다.

## 서버 계약 — 아직 Dev에 없음

로컬 초안: `supabase/proposals/202611040001_sos_alerts.sql`.
초기 Auth/care 마이그레이션에 의존하며 재연결 SQL과 별도로 승인·적용해야 한다.
모바일에서 스키마/RPC 부재 시 이용 불가를 표시한다. 성공을 로컬로 대체하지 않는다.

- `request_sos_alert()` → 양의 정수(수신 대상 수). 현재 인증된 환자만 호출.
- `acknowledge_sos_alert(alert_id uuid)` → void. 현재 승인된 해당 보호자만 호출.
- `sos_alerts` SELECT: 환자는 자신이 보낸 내역, 보호자는 자신의 수신 내역이면서
  현재 승인된 환자 연결만 조회. 직접 INSERT/UPDATE/DELETE 권한은 없다.
- 요청 시 환자 행 잠금으로 직렬화하고 30초 간격 제한. 승인 연결을 공유 잠금하여
  수신 대상 선정과 요청 저장 중 동의가 사라지는 경쟁을 막는다.
- 해제 후 보호자 조회·확인을 차단한다. 같은 두 계정이 재승인하면 과거 SOS 내역도
  다시 조회 가능하다(현재 동의 기준). 이 범위는 실제 적용 전에 확인해야 한다.
- SECURITY DEFINER는 빈 search_path, 명시적 객체 경로, 서버 사용자/역할 검증,
  PUBLIC/anon 실행 차단을 사용한다. 신뢰하는 소유자로 적용해야 한다.

## 로컬 검증과 미검증

`cd mobile; node --test scripts/test-sos.cjs`는 합성 응답·React 상태·타이머 Mock 검증이다.
DB RLS 실행이나 JWT, 기기 간 네트워크 전달을 증명하지 않는다.
SQL은 초안이며 실제 PostgreSQL 실행, 권한·동시성 실행 검증이 남아 있다.
기존 로컬 DB나 Dev에 자동 적용하지 않는다.

실제 적용 후 합성 환자 A/B, 보호자 G/H로 확인할 항목:

1. A-G 승인, A-H 대기: A 요청은 G에게만 생성, H/B/anon은 조회 불가.
2. G가 다른 기기 홈에서 수신·확인, A가 확인 시각 조회. H의 확인 RPC는 거부.
3. A-G 해제 후 G 조회·확인 차단. 과거 요청/확인 이력은 삭제되지 않음.
4. 보호자 없는 환자 요청 실패, 보호자 전송 실패, 환자 확인 실패, 만료 JWT 거부.
5. 동시 중복 전송의 한 요청만 성공, 나머지는 30초 제한. 각 보호자별 중복 없음.
6. 네트워크 중단·앱 이탈·만료 후 성공 안내를 잘못 표시하지 않는지 실기기 확인.

## 재연결 Dev 적용의 최소 남은 순서

기존 로컬 재연결 검증과 카탈로그 비교는 재검토하지 않는다. 기존 암호화 백업을
보존하고 최신 백업의 종료 코드·체크섬·아카이브 검증 결과를 확인한다. 실패했던 후속
읽기 조회는 별도 승인 후에만 진행한다. 실제 복원은 일정상 보류·미검증이다.

1. 백업 시점 이후 변경과 복원 미검증 위험 확인, 정확한 재연결 SQL 적용 별도 승인.
2. 승인된 파일만 Dev에서 실행(기존 UNIQUE를 활성 쌍 부분 UNIQUE로 변경,
   closure_reason 추가, 요청/해제 RPC 교체). 기존 이력을 삭제하거나 재활성화하지 않음.
3. 적용 직후 데이터 보존·함수/RLS 확인, 합성 JWT 요청→승인→해제→재요청 테스트.
4. 실패 시 COMMIT 전 ROLLBACK. COMMIT 후 새 이력을 삭제하여 옛 UNIQUE로
   되돌리지 않고, 쓰기를 중단한 뒤 이력 보존 수정안을 검토.
5. 재연결 확인 후 SOS SQL의 로컬 실행 검증·별도 Dev 승인·두 기기 테스트.

이번 작업에서는 DB 접속, 원격 변경, 백업 변경, 외부 AI 호출을 수행하지 않는다.

## 2026-11-05 실제 모바일 사용자 보고

대상 DrMAS-Dev/main, 합성 환자 A와 승인된 보호자 G.
사용자 보고 기준으로 A의 SOS 버튼 작동 및 A-G SOS 상호작용 확인은 PASS.
Codex가 직접 실행하거나 서버 기록을 조회한 결과는 아니다.

사용자의 추가 실기기 보고로 다음 네 단계가 각각 PASS로 확인됐다.

1. 환자 A의 SOS 요청: PASS (사용자 실기기 보고)
2. 보호자 G의 SOS 수신함 표시: PASS (사용자 실기기 보고)
3. 보호자 G의 SOS 확인 처리: PASS (사용자 실기기 보고)
4. 환자 A 화면의 '보호자가 확인함' 표시: PASS (사용자 실기기 보고)

서버 DB 값의 별도 검증 완료를 뜻하지 않는다. 서버 저장값·시각 자체는 미검증이다.

다음 최소 읽기 전용 검증은 G 일반 세션의 A SOS 조회 양성 결과를 먼저 확인하고,
H 일반 세션에서 auth.getUser 및 본인 profiles의 guardian 역할 조회 성공,
H-A 승인 연결 없음 확인 후 sos_alerts를 patient_id=A로 조회해 0행인지 확인한다.
추가로 patient_id=A, guardian_id=G 조건으로 G 수신 내역도 0행인지 확인한다.
SELECT HEAD/count만 사용하고 UUID/토큰/행 내용은 출력하거나 저장하지 않는다.
조회 오류/인증 실패를 차단 PASS로 보지 않는다. 개발 전용 RLS 진단에 SOS HEAD/count
검사를 추가했다. 같은 앱 실행에서 A와 G의 실제 SOS 양성 조회 후 B/H를 검사한다.
새 SOS 진단을 실제 계정으로 실행하기 전까지 B/H 실제 JWT SOS 차단은 미검증이다.

Dev 동시성, 해제 직후 동일 JWT의 접근 차단도 미검증이다. 현재 연결을 해제하거나
SOS를 재전송하지 않는다. 로컬 PostgreSQL PASS와 Dev 실행 결과는 구분한다.
개발 전용 진단 기능은 유지한다. 원격 쓰기/SQL 재적용/배포는 수행하지 않는다.
